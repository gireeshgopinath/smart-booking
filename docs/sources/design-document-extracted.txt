Booking Application Design and Development
Application specification and local AI development guide
Version 2.0  |  9 October 2026  |  Prepared for Gireesh Gopinath
Build decision
Build a guest booking platform that businesses can configure through a visual portal or an AI builder. Customers reserve and manage appointments without registering. The backend enforces capacity and policy; AI prepares suggestions and configuration drafts; customers and owners approve exact changes.
This document provides the application design and development route. The accompanying pack contains detailed requirements, API and data contracts, 42 implementation tasks, prompts, review templates and a portable blueprint schema. Application implementation and operational verification follow those tasks.
Scope carried forward
Guest website and authenticated business portal with staff, resources, appointments and capacity sessions.
AI-generated business blueprints, conversational changes, page composition, rehearsal and live change-impact previews.
Controlled agents, calendar and communication integrations, portable templates and operational recovery.
Cell-based scaling, Compose and Kubernetes deployment, CI and recovery evidence.
Dummy payment demonstration only with no card collection or money movement.

2 Product scope and releases
Pilot one low-sensitivity local-service segment in one launch market. A salon-like business provides the appointment use case; a synthetic class provider validates capacity. Staff authenticate, while customers use narrowly scoped guest capabilities. The initial application is provider software with shared links, not a cross-business marketplace.

Use cases
A customer books a haircut from a QR code without a password. A class operator allocates three of twelve seats. A rental reserves an asset and staff member together. A manager records a phone appointment using the same rules. An owner describes business hours and services, confirms inferred values and publishes a rehearsed blueprint. A staff absence produces approved replacement options rather than silent schedule changes.
Success measures
Proposed pilot targets are a standard booking median under 60 seconds, zero confirmed capacity violations and at least 90 percent successful completion across ten moderated synthetic tasks. Measure setup time, funnel abandonment, support contacts, occupancy, cancellations, recovered places and notification delays. These are planning targets, not results already achieved.
Commercial validation
Test whether verified setup and recovery reduce owner work and improve customer completion. Interview pilot businesses and measure retained use before selecting subscription pricing. Track infrastructure, inference and messaging cost per active tenant. Real subscription billing is outside this implementation.
3 Customer and business experience
Guest booking
The primary flow is service, live time, contact details, review and confirmation. Display duration, location, local time zone, party size, price and cancellation policy before the final action. One reachable contact channel is sufficient; optional business verification does not create a customer account.

Generate the idempotency key before a mutation. If the response is lost, query operation status before trying a new command. An expired hold or stale slot preserves contact input and offers alternatives. Do not silently queue bookings while offline.
Business portal
Provide location-aware calendar and booking lists, manual booking, service/resource/schedule configuration, pending approvals, attendance, integrations, insights and audit. Role restrictions apply to server APIs. Dragging an appointment opens an approved reschedule flow and never bypasses allocation constraints.
Builder experience
Describe the business, review extracted and inferred facts, resolve missing material values, preview the page, rehearse bookings, inspect affected appointments and approve the exact draft. Conversational edits show a before-and-after diff. Rollback creates another validated configuration version and preserves appointment history.
Accessibility
Target WCAG 2.2 AA. Verify 360-pixel mobile screens, keyboard navigation, focus, screen-reader errors, contrast and reduced motion. AI remains optional. Dates follow locale presentation with an explicit location time zone. Choose launch languages during the pilot.
4 Architecture and platform decisions
Use a modular Java 25 and stable Spring Boot 4.x core per tenant cell. Pin compatible versions after a dependency trial. Deploy routing, booking API, AI runtime and background workers separately for fault and resource isolation. The frontend uses React and TypeScript with a shared accessible component system.

Cell growth and single writer
Begin with one cell and verify two locally. The directory assigns a home cell and route epoch. Cell commands enforce a writer fence independently of cached routing. Migration pauses writes, drains commands, fences the source, copies and reconciles tenant state, then activates only the destination. Include pending jobs, approvals, guest capabilities and idempotency records.
Consistency boundaries
PostgreSQL is the final inventory authority. Static catalogue can be cached; availability cache and replicas only suggest slots. Commit booking state and outbox events together. Transport is at least once, with durable inbox deduplication. Multi-resource transactions remain within one tenant cell; cross-cell atomic scheduling is excluded.
The detailed Markdown architecture includes Mermaid topology and twelve decision records. Keep separate network services for independent resource usage rather than every domain noun.
5 Data model and booking correctness
Core records
Tenant directory, memberships, services, resources, schedules, exceptions, guest grants, proposals, approvals, holds, bookings, allocations, capacity sessions, idempotency operations, inbox/outbox, notifications, waitlists, calendar cursors, blueprints, impact reports, agent runs and simulated intents form the data model. Tenant-owned relationships use tenant-aware keys.
Reservation transaction
Resolve caller and tenant, validate the canonical request and claim the durable idempotency key.
Lock scheduling guard rows and capacity session rows in a stable order. Recheck current versions and authoritative database time after obtaining locks.
Expire relevant old holds under the same locks. A stopped sweep worker cannot make an expired hold valid.
Use half-open occupied intervals including buffers and an active-row PostgreSQL exclusion constraint for exclusive resources.
Conditionally reserve capacity for the whole party. Holds count against capacity; conversion to confirmed keeps the same allocation.
Validate exact caller approval, persist booking and outbox, save operation result and return success only after commit.
Rescheduling reserves the new allocation and releases the old one inside a transaction. A failed move preserves the original appointment. Multi-resource booking is all or none. Duplicate release cannot decrement capacity twice. A reused idempotency key with a changed payload returns a conflict.
Time and state
Store UTC instants, location IANA zones and accepted policy snapshots. Recurring hours are interpreted locally. Explicitly resolve ambiguous or nonexistent daylight-saving times. Holds become consumed, expired or released. Pending verification/approval consumes capacity only until a declared deadline. Cancellation, completion and no-show follow legal guarded transitions.
Guest and staff security
Guests hold hashed, random, scoped capabilities; object IDs and references are not credentials. Management links exchange a fragment token into a scoped session. Staff require verified OIDC and active membership. Runtime database roles cannot bypass row security; pooled transaction context must not leak between tenants.
6 Intelligent blueprints and controlled agents
Builder pipeline
Extract authorized business facts, record supplied/inferred/unresolved provenance, clarify material gaps, create a typed draft, validate structure and semantics, compose trusted page components, rehearse bookings, compute current impact and obtain exact owner approval before publication. AI produces configuration data rather than executable page code.
The included starter schema and synthetic salon example establish portable service/resource/schedule keys and policy settings. Implement complete provenance, reference checks, schema migration and publication rules in T31. Import always creates a server-owned draft; a supplied status cannot authorize publication.
Rehearsal and impact
Rehearsal runs shared scheduler code against isolated synthetic data and cannot message real customers. Cover holidays, buffers, last-seat contention, expiry, multiple resources and daylight saving. Impact reports bind a draft hash to current configuration and affected booking versions. New conflicting appointments invalidate an old preview. Existing reservations remain valid until separately approved moves succeed.

Server control
Approval is a server-issued, scoped, expiring record bound to exact proposal hash and version. A model statement cannot approve itself. Tools receive trusted caller/tenant context, not model-provided authority. There are no arbitrary SQL, shell or infrastructure tools. Activities perform inference; durable workflow logic remains deterministic.
Bound inference and tool calls, deadlines, token use and queue length. On model timeout, expose manual booking. Evaluate intent extraction separately from unauthorized actions. Any forged approval, tenant leakage or invented confirmation blocks release.
7 Integration and customization design
Connector lifecycle
Use a registry with typed capabilities, configuration, scopes, field mappings, connection test, health and revocation. Owners approve permissions and preview synthetic mappings. AI may suggest a mapping but cannot grant consent. Store credentials outside blueprint exports and model context.

Calendar behavior
Import external busy events with provider mapping and incremental cursors. Use Google sync tokens and Microsoft calendar-view delta links with their query scopes. Reconcile missed notifications and prevent exported-event echo loops. External edits create a staff-visible conflict rather than silently moving a guest booking. Stale mandatory calendars restrict affected new inventory by policy.
An external event can conflict immediately after synchronization. Local booking transactions cannot make external calendar writes atomic; detect and reconcile that boundary explicitly.
Safe customization
Offer branding, rules, low-sensitivity forms, declarative automation recipes and reviewed connector adapters. Page components and transformation functions come from trusted registries. Portable blueprints reference logical resources and integrations without credentials or customer records. Import and rollback require fresh validation and impact review.
Simulator rules
All simulated intents, receipts and reports say SIMULATED NO MONEY MOVED. Scenario controls are operator-only in local/demo profiles. Test success, decline, timeout, duplicate, reordered, invalid and late callbacks. Late simulated success cannot take another guest slot; record a compensating simulated refund. No real gateway SDK, card fields or financial credentials exist.
8 Deployment scale and recovery
Compose provides real local PostgreSQL, cache, OIDC, queues, workflows, mail inbox and application services. Verify the same immutable images in a dedicated booking-dev kind cluster. Cloud templates cover private AWS dependencies, EKS, secrets, workload identity, TLS and backup; actual paid provisioning requires a selected authorized target.

A million concurrent browsers making one request every thirty seconds implies about 33,333 requests per second before bursts or AI. That is a separate tier. Twenty agent starts per second with three model calls creates sixty inference requests per second. At two thousand input tokens per call, input load is 7.2 million tokens per minute before output. Local GPU development does not establish that capacity.
Measurement and operations
Declare dataset, tenant skew, duration, offered/achieved rates and load generator limits. Separate expected inventory conflicts from errors. Planning objectives are server p95 below 500 ms for availability and below one second for mutations, with zero capacity violations and bounded queues. Monthly 99.9 percent core availability needs operational evidence beyond a load test.
Use API pool limits, fair tenant admission, HPA/KEDA and independent AI quotas. Observe outbox/queue age, database wait, calendar freshness and model latency. Run isolated backup/restore and rollout drills. Proposed recovery objectives are RPO at most five minutes and RTO at most sixty minutes, subject to actual tests. Helm rollback does not reverse database migrations.

Evidence contract
For each task record dependencies, changed files, source revision, commands, actual exit codes, timestamps, evidence paths and limitations. PASS means acceptance criteria were run and met. FAIL and BLOCKED remain visible. Do not turn contract tests into live integration claims or mark unavailable external gates passed.
Suggested first slice
Establish the baseline, then tenant authorization and database invariants. Add catalogue and availability, scoped holds and idempotent confirmation. Prove the last-seat race before building the guest UI. Use that complete journey as the first major checkpoint. The AI builder extends a reliable scheduler, not a mocked booking path.
Task count is not a time estimate. Estimate after the foundation and first slice using actual local-model repair rate. The task JSON is navigation metadata; full task prose contains the implementation and acceptance requirements.
10 Local model work with ChatGPT guidance
Use your local coding model for implementation and tests; use ChatGPT for design decisions, difficult defects and focused review. ChatGPT does not automatically see or supervise your local repository. Send a review packet and relevant patch/source. Product AI inside the finished application is a separate system.
Local setup
Check actual GPU memory, quantization, context and tool behavior on your RTX 5080 machine. Load a working coding model in LM Studio, start its localhost server and copy the exact served model ID. Capability trial
In a temporary repository, ask the agent to read a file, change one function, write an independent behavior test, run it and inspect the actual diff. Verify honest failures and bounded repair. If tools fail, use reviewed patch mode rather than autonomous implementation.

Independent readiness labels
Report backend, frontend E2E, Compose, local Kubernetes, AI contracts, live local model, blueprint builder, MCP/A2A, live external calendars, cloud templates, cloud deployment, scale and experimental features separately. A calendar fixture is not a live-account test; Terraform validation is not a deployment; local throughput is not proof of a million-user service.
Threat controls
Scope and hash guest capabilities, verify business identity and membership, enforce CSRF/CORS, limit holds and recovery attempts, redact secrets and use runtime database roles without RLS bypass. Imported text and model output cannot acquire authority. Use typed tools and trusted components. Validate webhook destinations and block private-address egress. Fence stale writers during migration.
Completion statement
Local P0/P1 acceptance requires every mandatory available gate to pass. Missing external account or large-scale evidence remains explicit. Experimental voice, demand advice and multi-stage work stay flagged with their actual prototype status. The design pack specifies these checks; application behavior will be verified during development.
